# Граф денег

Восстановление финансовой структуры организованной группы по транзакционной сети.

Вход — выгрузка исходящих переводов 81 клиента на 4 колена (2 248 узлов, 3 119 рёбер,
4 840 транзакций, июль 2026). Выход — роль каждого узла с обоснованием, кластеры сети
и ранжированный список: **кого из 2 248 клиентов смотреть первым и почему**.

## Запуск

```bash
./run.sh
```

Ставит зависимости и считает всё от сырых `.parquet` до трёх выгрузок в `out/`.
Полный пересчёт — **около 3 секунд** на обычном ноутбуке (лимит по ТЗ — 5 минут).
Ни GPU, ни облака, ни внешних сервисов.

Вручную, если нужно подробнее:

```bash
pip install -r requirements.txt
PYTHONPATH=src python3 -m moneygraph.pipeline --data data --out out
```

## Что на выходе

| Файл | Строк | Содержание |
|---|---|---|
| `out/nodes_roles.csv` | 2 248 | роль, уверенность, кластер, приоритет и обоснование по каждому узлу |
| `out/clusters.csv` | 91 | размер, число seed, внутренний оборот и гипотеза по каждому кластеру |
| `out/top_nodes.csv` | 25 | ранжированный список на проверку с обоснованием |
| `out/features.parquet` | 2 248 | все посчитанные признаки — для интерфейса и перепроверки |
| `out/summary.json` | — | сводка прогона: время, распределение ролей, факты о датасете |

`nodes_roles.csv` содержит обязательные колонки схемы ТЗ (`gid`, `role`, `role_score`,
`cluster_id`, `priority_score`, `evidence`) **и все признаки, на которых построена роль** —
любую строку можно перепроверить, не заглядывая в код.

## Как устроен пайплайн

```
data/*.parquet
   -> loading.py    загрузка и проверки целостности
   -> graph.py      направленный взвешенный граф (все 2 248 узлов, включая 19 без рёбер)
   -> features.py   структура + достижимость от seed + временны́е паттерны
   -> clusters.py   Louvain по неориентированной проекции
   -> roles.py      правила с порогами -> роль, уверенность, evidence
   -> priority.py   взвешенный приоритет -> кого смотреть первым
   -> out/*.csv
```

## Критерии ролей

Правила проверяются **в порядке приоритета**, первое сработавшее определяет роль.
Все пороги собраны в `src/moneygraph/config.py` и привязаны к распределениям
в этом датасете, а не взяты произвольно.

| Роль | Правило | Порог и почему именно такой |
|---|---|---|
| `coordinator` | собирает **и** перераспределяет: `in_deg ≥ 5` и `out_deg ≥ 10` и `in_kzt ≥ 0.3 × out_kzt` | требование баланса потоков отсекает узлы, которые не собирают, а вливают средства извне выгрузки |
| `coordinator` | либо структурно: посредничество в верхнем 1%, деньги доходят от ≥ 3 seed, связывает ≥ 2 кластера | узел, через который проходят пути от нескольких независимых seed — это структура, а не совпадение |
| `consolidator` | `in_deg ≥ 5` и `in_deg ≥ 2 × out_deg` | 1 760 узлов имеют ровно одного плательщика; порог 5 отсекает верхние 2.3% (51 узел) — это уже не бытовые переводы |
| `distributor` | `out_deg ≥ 10` и `out_deg ≥ 2 × in_deg` | 1 554 узла не отдают вовсе; 10+ получателей — у 64 узлов (2.8%) |
| `transit` | есть вход и выход, коэффициент пропуска `out_kzt/in_kzt` в 0.7–1.3, узел не seed | окно вокруг единицы = «принял и отдал столько же»; seed исключены, у них входящие занижены устройством выгрузки |
| `terminal` | `depth ≤ 3` и удержано ≥ 80% полученного | глубина ≤ 3 обязательна: на 4-м колене отсутствие исходящих — артефакт обхода |
| `terminal_unverified` | `depth = 4`, исходящих нет, но получено заметно (≥ 2 плательщика или сумма выше медианы) | **расширение словаря**, см. раздел ниже |
| `peripheral` | ни один порог не пройден | — |

`role_score` (0–1) — уверенность в роли. Она снижается, когда вывод опирается на
оборванную выгрузку, и масштабируется объёмом: транзит на одной операции у порога
5 000 ₸ получает низкую уверенность, а не единицу.

### Расширение словаря: `terminal_unverified`

ТЗ допускает расширение словаря при условии документирования. Мы ввели одну
дополнительную роль, потому что без неё решение обязано врать.

444 узла лежат на 4-м колене и не имеют исходящих. Наивное правило
«`out_deg = 0` ⇒ конечный получатель» назвало бы их стоками — но обход просто
закончился на них, а не деньги. Из этих 444 у 183 узлов входящий профиль
действительно похож на сток; они получают роль `terminal_unverified`
с прямой формулировкой в `evidence`:

> «Принял 300 тыс ₸ от 1 плательщика, исходящих нет — но узел на 4-м колене,
> где обход остановлен. Отличить конечного получателя от необследованного
> нельзя без выгрузки на 5-е колено.»

Настоящий `terminal` присваивается только при `depth ≤ 3`, где отсутствие
исходящих — это поведение узла, а не граница выгрузки. Таких узлов 1 185.

## Приоритет: кого смотреть первым

```
priority = ( 0.30·роль + 0.22·seed_sources + 0.18·betweenness
           + 0.15·оборот + 0.10·pagerank + 0.05·охват ) × (0.6 + 0.4·role_score)
```

Компоненты нормируются на 0–1 по выборке. Множитель по `role_score` опускает
в списке узлы, у которых роль присвоена на слабом основании.

`seed_sources` — от скольких **разных** seed-клиентов деньги доходят до узла.
Это самый содержательный признак в задаче: совпадение нескольких независимых
seed на одном узле означает структуру, а не случайность.

В `top_nodes.csv` колонка `why` называет два главных вклада в ранг — чтобы
позицию в списке можно было оспорить по числам.

## Как учтены ограничения датасета

| Ограничение | Что сделано |
|---|---|
| Обход оборван на 4-м колене (444 узла) | `terminal` только при `depth ≤ 3`; отдельная роль `terminal_unverified` |
| Видны только исходящие переводы | `pass_through` не применяется к seed; узлы, отдающие втрое больше видимых входящих, помечаются в `evidence` как «источник средств вне выгрузки» |
| У seed входящие занижены | роль `transit` для seed не назначается вовсе |
| Порог 5 000 ₸ | дробление ниже порога невидимо — заявлено в ограничениях, на этом выводы не строятся |
| 19 seed без единого ребра | попадают в выгрузку как `peripheral` с явным указанием причины |
| 16 слабосвязных компонент | кластеризация Louvain, 91 сообщество; 8 из них содержат более одного seed |
| Louvain теряет направление | кластеры отвечают только на вопрос «кто с кем связан»; все роли считаются по направленному графу |

## Ограничения подхода

Это **гипотезы для проверки, а не выводы о виновности.** Формулировки в `evidence`
намеренно даны как «признаки консолидации», «признаки транзита».

Размеченных ролей в данных нет, поэтому точность в привычном смысле не измеряется —
критерии защищаются обоснованностью правил, а не accuracy.

Роли назначаются по структуре и суммам за один месяц. Внутрибанковский периметр,
порог 5 000 ₸ и глубина 4 колена означают, что часть сети принципиально невидима:
у 354 узлов исходящие превышают видимые входящие, и источник этих средств лежит
за пределами выгрузки.

Betweenness считается структурно, без весов: веса-суммы нельзя подавать
как длину пути, а инвертировать их — значит вводить произвольную шкалу.

## Масштабирование до ~1 млн узлов

Текущий пайплайн — 3 секунды на 2 248 узлах, но узкие места известны и упрутся
не в загрузку, а в две метрики.

**Betweenness** — O(V·E), на миллионе узлов неприменим. Замена: приближение
Брандеса по выборке опорных вершин (`k` семплов вместо всех) либо переход
на `graph-tool`/`igraph` с параллельной реализацией. Точное значение здесь не нужно,
нужен ранг.

**Louvain** на питоне заменяется на Leiden из `igraph` — он и быстрее, и не даёт
несвязных сообществ.

**Достижимость от seed** уже масштабируется: это по одному BFS на seed, а не на узел.
При росте числа seed до тысяч — переход на разреженное матричное умножение булевых
масок достижимости.

**Хранение и признаки** переезжают с pandas на DuckDB или Polars: агрегации по рёбрам
и транзакциям — обычные group-by, они считаются вне памяти.

**Что не изменится:** правила ролей. Они опираются на локальные признаки узла
(степени, суммы, коэффициент пропуска) и считаются за один проход независимо
от размера графа. Пороги, привязанные к перцентилям, пересчитываются на новой выборке.

## Структура репозитория

```
src/moneygraph/
  config.py      все пороги с обоснованием
  loading.py     загрузка parquet и проверки целостности
  graph.py       построение направленного графа
  features.py    признаки: структура, seed-достижимость, время
  clusters.py    Louvain и гипотезы по кластерам
  roles.py       правила ролей и генерация evidence
  priority.py    ранжирование
  text.py        склонение числительных для читаемых формулировок
  pipeline.py    CLI: один запуск от parquet до выгрузок
data/            предоставленный датасет
starter/         стартовый код организаторов (не используется в пайплайне)
out/             выгрузки
```
