# Журнал решений

Почему сделано именно так. Пишется, чтобы решения не переоткрывали заново
и не ломали случайно. Каждое решение с последствиями и, где есть, со сторожевым тестом.

## 1. `terminal` только при depth ≤ 3

**Проблема.** 444 узла лежат на 4-м колене и не имеют исходящих. Обход остановился
на них — это граница выгрузки, а не поведение денег.

**Решение.** Роль `terminal` присваивается только при `depth ≤ 3`. Для узлов
4-го колена с похожим входящим профилем введена документированная роль
`terminal_unverified` (183 узла) с прямой формулировкой в evidence: отличить
конечного получателя от необследованного нельзя без выгрузки на 5-е колено.

**Почему не проще.** Наивное `out_deg = 0 ⇒ сток` дало бы 444 ложных конечных
получателя — это прямо названо ловушкой в материалах организаторов.
Остальные 261 узел 4-го колена уходят в `peripheral`: их входящий профиль
не даёт оснований даже для гипотезы.

**Сторож.** `test_terminal_is_never_assigned_at_truncated_depth`.

## 2. Seed никогда не `transit`

**Проблема.** Граф собран **от** seed по исходящим, поэтому деньги, полученные
ими извне выборки, в данных отсутствуют. Коэффициент пропуска у seed доходит до 20+.

**Решение.** Правило транзита пропускает seed целиком, а не пытается их
скорректировать: корректировать нечем, входящих данных просто нет.

**Сторож.** `test_seed_nodes_are_never_classified_as_transit`.

## 3. Координатор требует баланса потоков, а не только степеней

**Проблема.** Первая версия правила назначала координатором узел по степеням:
`in_deg ≥ 5` и `out_deg ≥ 10`. Под него попал узел, получивший в графе 985 тыс ₸
и раздавший 23 млн. Evidence утверждал, что он «собирает от 5 плательщиков» —
это было неверно по сути: он не собирает, он вливает деньги извне выгрузки.

**Решение.** Добавлено условие `in_kzt ≥ 0.3 × out_kzt`. Узлы без баланса идут
как распределители, а в evidence появляется «отдаёт в 23× больше видимых
входящих: источник вне выгрузки». Структурный путь к роли координатора остался:
верхний 1% посредничества + деньги от ≥ 3 seed + связывает ≥ 2 кластера.

**Побочная польза.** Формулировка про источник вне выгрузки закрывает бонусный
пункт ТЗ про оценку полноты: она говорит аналитику, какую выгрузку запрашивать
следующей. Таких узлов в графе 354.

**Сторож.** `test_coordinator_requires_balanced_flow_not_just_degrees`.

## 4. Уверенность в роли масштабируется объёмом

**Проблема.** Транзит на одной операции в 5 000 ₸ (минимальная сумма в выгрузке)
получал `role_score = 1.0`: формально он пропустил 100% полученного.

**Решение.** Уверенность транзита умножается на объём с выходом на полку
к 2 млн ₸. Одна операция у порога больше не выглядит как транзитная инфраструктура.

**Сторож.** `test_transit_confidence_scales_with_volume`.

## 5. Evidence собирается по бюджету важности

**Проблема.** Лимит ТЗ — 200 символов. Простая обрезка резала строку на полуслове
и выбрасывала самые содержательные признаки, потому что они стояли в конце.

**Решение.** `text.compose()` добавляет фрагменты по убыванию ценности, пока
они влезают. Порядок: прямой возврат денег отправителю → источник вне выгрузки →
замкнутая цепочка → точка сочленения. Роль не дублируется в тексте: она уже
есть отдельной колонкой, и её упоминание съедало бюджет.

**Сторож.** `test_evidence_never_exceeds_limit_with_every_extra_present`.

## 6. Все артефакты воспроизводятся побайтово

**Проблема.** Два одинаковых прогона давали разные файлы. Причины: многопоточный
scipy даёт расхождения ~1e-16 в HITS, и `-0.0` отличается от `0.0` при записи в CSV.

**Решение.** Все float округляются перед записью, `+ 0.0` сводит знаковый ноль
к обычному, сортировка выгрузок имеет вторичный ключ `gid` для устойчивого
порядка при равных приоритетах.

**Почему это важно.** Воспроизводимость — отдельный критерий оценки на 25 баллов.
Плюс при передаче работы иначе каждый прогон создавал бы пустые диффы.

**Сторож.** `test_runs_are_byte_identical`.

## 7. Betweenness считается без весов

Суммы переводов нельзя подавать в `betweenness_centrality` как длину пути:
там вес означает расстояние, и «дорогое» ребро стало бы менее проходимым.
Инвертировать суммы — значит вводить произвольную шкалу. Поэтому посредничество
считается структурно и отвечает на вопрос «кто стоит на путях», а влияние
с учётом сумм даёт взвешенный PageRank.

## 8. Кластеризация теряет направление — и это оговорено

Louvain работает только на неориентированном графе. Кластеры отвечают на вопрос
«кто с кем связан», а все роли считаются по направленному графу. Получилось
91 сообщество, из них 8 содержат более одного seed — совпало с оценкой
организаторов.

## 9. Интерфейс — один HTML-файл, а не веб-приложение

Cytoscape вшит в страницу, данные встроены как JSON. Ни сервера, ни npm,
ни интернета: жюри открывает файл двойным кликом, и это работает на любой машине.
Альтернатива в виде React + Vite требовала бы `npm install` у проверяющего
и конфликтовала с требованием «одна команда на чистой машине».

Схема не рисует все 2 248 узлов сразу — это нечитаемо. По умолчанию показывается
топ приоритета с окружением (около 450 узлов), остальное открывается поиском,
фильтрами и переключателем охвата.

## 10. Роли — гипотезы, а не обвинения

Формулировки в evidence: «признаки консолидации», «кандидат в организаторы».
Требование ТЗ, раздел «Осторожность формулировок». Инструмент не измеряет
виновность и не имеет для этого данных: размеченных ролей в датасете нет,
критерии защищаются обоснованностью правил, а не accuracy.

## 11. React-приложение дополняет автономный HTML

Для рабочего места аналитика добавлены React + TypeScript и локальный FastAPI.
Это отдельный режим `make web`; исходный `./run.sh` по-прежнему создаёт HTML,
который открывается без сервера и Node.js. Веб-приложение использует результаты
того же расчёта, а не отдельные правила ролей.

API отдаёт один воспроизводимый снимок `dashboard.json`, загруженный при старте.
Для текущих 2 248 узлов фильтрация в браузере достаточно быстрая, а единый снимок
исключает рассогласование разделов. При росте графа понадобятся серверная фильтрация
и выдача подграфов. Идентификаторы передаются строками, поскольку превышают
`Number.MAX_SAFE_INTEGER` в JavaScript.

В гипотезах кластеров исправлен внутренний оборот: теперь это сумма только
внутренних рёбер (`sum_kzt_internal`), а не сумма оборотов участников, которая
повторно учитывала внутренние переводы и включала внешние связи.

## 12. Граф раскрывается от задачи аналитика

Общий граф из сотен участников плохо читается. В React-интерфейсе первый экран
агрегирует переводы между кластерами: суммы и число операций складываются по
направленной паре сообществ, внутренние рёбра исключаются. По умолчанию видны
15 крупнейших сообществ и 30 крупнейших межкластерных потоков; скрытые элементы
обозначены счётчиками и доступны через увеличение охвата.

Для исследования конкретного участника показываются крупнейшие десять входящих
и десять исходящих контрагентов. Центр и выбор — разные состояния: чтение карточки
не перестраивает окружение. Соседи раскрываются постепенно, общий предел — 150 узлов.
Фильтры относятся к соседям, центр остаётся доступным даже при несовпадении.
Положение узлов задаётся через Cytoscape preset: входящие слева, исходящие справа,
встречные контрагенты над центром. Ручные позиции, масштаб и панорамирование сохраняются
для каждого центра и охвата. Рёбра и участники также доступны в списках под схемой.

**Проверки:** агрегация межкластерных потоков, отдельные встречные направления,
отсутствие дубликатов, лимиты раскрытия, сохранение позиций и масштаба, старые ссылки
и адаптивность на 1440/1024/390 px.
